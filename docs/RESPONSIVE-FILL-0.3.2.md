# 0.3.2：更快的 MCP 响应与更可靠的填写闭环

## 基线与本次范围

基于已合并的 `9cbcac860aa4080cd638eda0b49233de281aa9b7`（PR #1；tree `8324356ffb42ba3ea212f77cb92843204c50be5a`）。扩展、Node 包和桥接为 0.3.2；通知协议为 2；控件引擎仍为 0.4.1，文件未修改，500ms 最终回读没有缩短。

这次改进桥接准备、命令到达延迟、重复请求、执行事务和现有 MCP 界面。未实现或同步完整独立加密工作台；现有主档仍在本机明文 JSON 中。没有新增权限、遥测、模型 API、云存储或自动提交。

## 实现

| 问题 | 本轮实现 | 保护边界 |
| --- | --- | --- |
| 每 1500ms 取一次指令，存在空等 | `/events` 最长20秒的有界通知等待；变化时立即唤醒，再由 `/poll` 取命令 | 通知不包含命令和资料，取消等待不会消费命令；关闭后迟到的命令丢弃而不是执行或重放 |
| 历史映射对每个字段再遍历全表 | `field-memory.mjs` 单次字段索引、唯一键计数与相关事实索引 | 重复经历仍须消歧；不跨扫描或主档更改复用索引 |
| 扫描与计划、开始与计划各两次请求 | `/snapshot` 可一并返回计划；`/begin` 返回服务器筛选后的本次计划 | 只下发本次选择；重新核对 URL、主档、计划有效期与所有权 |
| 重复打开或断网后反复发请求 | 单消费循环、代际标记、1—15秒退避、可取消等待 | 只重连通知，不自动重试网页写入；打开的助手切换到 Codex 不主动断线 |
| 多个岗位窗口可能抢计划 | 计划读取、开始、停止、结果校验 owner；扫描命令绑定 owner 与旧扫描ID | 仍是一个选中任务，不是多站点并行执行引擎 |
| 取消后过早解锁 | 停止请求先进入 stopping；收到执行器结果再释放 | 已写值保留，不回滚；取消不等于证明网页已经停止 |
| 回读缺项或重复导致误记成功 | 授权字段集合校验；拒绝重复、未知和未选字段；缺项记 not-attempted | 不以排队、发出或缺失回执当成功；仅已回读的唯一字段保存历史映射 |
| 记录写失败卡住填写锁 | 完成结果先落内存并释放，再保存历史映射和计数审计 | 持久化失败明确警告，不触发重新填写；不把任意字段错误文本写进审计 |
| 面板大批量渲染、失败信息不清楚 | Fragment 批量创建、结果行索引、全选/取消选择、停止按钮与逐字段状态 | 内容只以文本显示；失败后旧计划作废；390px 窄屏避免页面横向溢出 |

`ChangeSignal` 限制最多64个等待连接，关闭、断开和超时都清理定时器/监听器。桥接状态变更串行化，但通知和 MCP 等待扫描响应不占状态锁，避免互相等待。`form_scan` 自动重扫不能延长原共享授权；主档变化、用户切换目标或预览超过5分钟后须重新扫描。

已有 `resume-*` 网站自动显示配置在扩展更新事件中补入 `poll-loop.js`，不申请新来源权限。工作台和抽屉只在用户打开/连接时监听；收起或离开页面停止监听。为正常切到 Codex 对话，未把 `document.hidden` 等同于用户关闭；浏览器冻结、休眠、后台回收仍可能中断，不保证后台常驻。

## 性能测量：不要混淆三个时间

原始完整记录为 [measurements.json](benchmarks-transport/measurements.json)。Node v22.16.0 / Linux；每项6对，交替顺序，保留每次记录及被测文件 SHA-256。无真实简历、招聘网站、模型请求或申请提交。

### 命令通知到达

同一个新桥接进程、真实认证 localhost HTTP + stdio MCP；一臂复现旧1500ms固定轮询策略，另一臂使用事件通知。两臂不是两套完整浏览器安装。任务到达相位预先固定为100、400、700、1000、1300、250ms，以避免只挑最有利时机；从发出工具请求计时，到客户端解析收到命令停止。之后另核对命令类型、标签页、计划ID和扫描ID。

| 通知阶段 | 中位延迟 | 独立核对 |
| --- | ---: | --- |
| 固定1500ms轮询 | 952.20ms | 6/6 |
| 事件通知 | 5.38ms | 6/6 |

**5.38ms 不是完成简历填写的时间。** 此项不包括模型推理、DOM扫描、字段输入、最终回读、网络上传或网页服务器保存。只说明这个本机小样本中，去掉固定等待后命令更快到达。浏览器后台调度和其他电脑会影响实际延迟。

另一个相同6秒空闲窗口测得：固定轮询4次请求，通知方式2次（初始读取及仍等待的通知请求）；窗口实际约6012ms，不据此宣称所有运行时固定节省某个比例。

### 资料准备

在相同虚构输入上，将旧桥接的嵌套“历史映射 + 相关事实筛选”公式与新索引实现交替运行，结束后对映射对象和相关事实数组做完全相等比较。每个规模6对，不包含磁盘读取、整张表计划生成、DOM操作或模型调用。

| 规模 | 嵌套参考算法中位 | 索引算法中位 | 独立相等检查 |
| --- | ---: | ---: | --- |
| 160字段/事实 | 56.90ms | 1.25ms | 12/12 |
| 500字段/事实 | 424.22ms | 4.05ms | 12/12 |

总计36次（12次通知、24次准备）均核对通过。这些是分阶段、小样本、合成数据测量，不是“全部网站整体快多少”的结论。对照函数和通知策略保留在驱动中，被测来源固定为上述主线提交；基线不是上轮0.4.0本地工作台。

## 未完成与恢复边界

没有本次安装后MV3验收、真实北森/Moka/智联/国聘等官网验收、跨域iframe通用支持、全部复杂级联、服务器回执验证或塔塔对照评测。已有内容不覆盖，未知资料不猜，验证码、同意声明和最后提交仍由用户操作。

停止不会撤回已填数据，网页可能在输入时自动保存。浏览器/进程在执行中崩溃可能留下未确认的执行状态；不要自动重复执行或删除私有资料。先核对网页，再只重启 resume_fill 桥接并重新扫描，不能宣称已实现跨崩溃的精确恢复。

旧主档和证据文件仍是本机明文；使用 Codex 时共享内容进入其上下文，填入网页的内容交给招聘网站。新审计仅保存状态/计数；历史版本已写出的日志不会被自动清除。

## 机制参考

沿用 [Jev Ultrafast的分阶段观察、独立核对和完整测量方法](https://github.com/browser-use/jev-ultrafast/blob/452c1ad2dd628008f1d5608f28158d76e49e6cc0/docs/performance.md)，代码独立实现。平台约束参考 [Chrome service worker生命周期](https://developer.chrome.com/docs/extensions/develop/concepts/service-workers/lifecycle)、[AbortController](https://developer.mozilla.org/en-US/docs/Web/API/AbortController) 和 [Node HTTP](https://nodejs.org/api/http.html)。响应关闭用于取消等待，而不是把已读完的请求流关闭误判为客户端离开。20秒等待与23秒客户端截止是实现选择，不是常驻后台保证。

## 4 内置浏览器演示的能力门槛

必须区分以下验证层：

| 层级 | 可证明什么 | 不可代替什么 |
| --- | --- | --- |
| DOM/逻辑夹具 | 规则、事件、回读及反例 | 扩展安装、真实登录页面 |
| 内置浏览器中的本地演示页 | 用户能看到真实 UI 和同一引擎在夹具中运行 | MV3 后台、storage、权限及真实网站执行 |
| 已安装 MV3 的隔离浏览器 | 扩展真实消息与存储链路 | 用户现有登录态页面 |
| 用户指定内置浏览器中的真实页 | 该页面当前实例的操作结果 | 没有插件实例证据时，不能证明由插件完成 |

本次工具返回的内置浏览器能力只有页面操作、只读 DOM、截图、页面日志及列出的页面能力；未暴露扩展安装/重载能力。官方浏览器文档说明它有独立 profile，但没有在所读页面提供加载第三方 unpacked 扩展的流程。结论是“本会话尚未证实可在此宿主加载项目扩展”，不是“内置浏览器一定不支持扩展”。

实施阶段首先检查已有插件入口或宿主正式支持的加载机制，并取得以下完整证据：

- 当前浏览器/标签页、产品版本、引擎版本、扩展实例或正式宿主实例、source revision。
- 可从真实页触发插件 UI，并在可信扩展端收到同一个 taskId。
- 执行来自插件自己的 plan/executor，产生同一任务的完成回执。
- 原登录态和扩展资料保留。

如果仍没有受支持的加载方式，不清空真实表单。继续完成可独立推进的源码、恢复演练、夹具、安装回归与日志工作，但真实内置浏览器插件验收保持 blocked。向用户说明缺少的具体宿主能力，再由用户决定提供受支持入口或接受另一个浏览器作为额外验收环境；不能擅自换成 Edge/Chrome 后宣称满足内置浏览器要求。

禁止借未文档化通道注入脚本、伪造 `chrome.runtime`，或让 Codex 逐字段填写来冒充插件演示。若做同源核心演示页，报告必须写“核心演示”，且本次真实插件验收条件仍未完成。浏览器自动化只负责触发插件 UI、必要的测试准备、独立观察与恢复。

## 5 原状备份、清空和恢复

### 5.1 两份独立记录

清空前建立本地私有会话目录，置于仓库外；不得进入 Git、PR、发行 ZIP 或公开 CI。最低包含：

- `baseline.json`：独立观察器读取的完整表单原状。
- `profile-backup.json`：扩展资料库备份，覆盖所有简历版本、原始条目、修订与作用域。
- `field-map.json`：可编辑字段、逻辑记录、原页面位置和恢复动作的对应表。
- 分区截图：用于确认可见展示，不取代值记录。
- `session-journal.jsonl`：准备、清空、执行、恢复的逐阶段结果。
- `restore-report.json`：最终原状比对与未恢复项。

备份不仅保存 input.value。每个逻辑字段须记录 section、recordOrdinal、label、controlKind、原始值、显示值、规范化值、checked、disabled、readOnly、日期精度、至今、换行、当前可见性、是否可恢复。附件只记录现有名称与存在状态，必要的下载/上传另走受支持流程；不假设 file input 能用字符串恢复。

备份必须由独立读取路径与插件扫描结果交叉核对：插件目前会漏识别，不能让相同漏识别逻辑同时定义正确答案和验收答案。若读取被脱敏、字段折叠不可见或恢复值不完整，将字段标为不可清空，不能把 `<redacted>`、占位词或截断文本当作原值。

### 5.2 清空前硬条件

全部满足才能清空：

1. 备份文件可重新解析，18 段记录的数量、顺序、字段和非空内容均有映射；以执行当天实际数量重新确认。
2. 已在私有隔离副本或虚构夹具完成相同控件的恢复演练，并独立回读通过。
3. 明确清空动作影响：页面本地状态、草稿、在线简历或已提交申请。网站自动保存行为无法确认时，不试探性删除已有数据。
4. “同步更新在线简历”等站点级选项有明确处理方案与原值记录。仅取消勾选不能证明网站无自动保存。
5. 插件运行身份已核实，日志可导出，恢复入口可用。
6. 所有拟清空字段都有预期来源与恢复值；未获完整备份、无恢复路径的字段排除并单列。
7. 清空范围是当前表单，不触及申请记录、附件、照片、账号、同意声明或扩展资料。

用户已经授权后续记录、清空和重新填写；实施时不再为同一可恢复范围反复询问。若发现会永久删除已投申请、改变新的站点/数据范围或超出既有授权，才需要在那一动作前说明后果并取得相应确认。

### 5.3 分两种复现，避免把问题混在一起

- **清空字段、保留卡片**：验证标签、取值、映射和控件执行。先做这一轮，保留记录位置。
- **零卡片/缺卡片**：验证新增与绑定。先在夹具做全部五类记录；真实页只在确认卡片删除可恢复且无不可逆副作用后执行。不能为了覆盖新增测试删除已提交历史。

清空必须经正常组件交互执行，并读取显示值和选中状态确认。清空搜索框不等于清空下拉值。写入前记录实际已清空集合，不把未清空项算作插件成功填写。

### 5.4 恢复规则

执行中断、版本不符、日志丢失、异页跳转、字段漂移或写错记录时立即停止新的写入，先核对已发生动作。对未知结果先回读，不盲目重试。

恢复依据 baseline，不依据“最新导入的简历”或失败的填写计划。恢复前再次检查当前字段，用户在演示期间新编辑的内容单列冲突，不静默覆盖。默认演示结束恢复到原有记录数量、顺序、值、附件存在状态和站点开关；若插件填写本来就与原状一致，仍要核对。

恢复动作与插件填写成绩分开记录。人工恢复、工具辅助恢复均不得计入插件自动成功率。现场无法恢复时保留页面和备份，明确列出具体字段，继续完成不影响恢复的其他工作。

## 6 目标架构与数据契约

延续已存在的 `src/autofill` 分层与 `extension/core`。拆分以独立职责和可复现缺陷为依据，不以重命名目录作为重构成果。

### 6.1 核心数据结构

以下为拟议契约，实施可采用 JSDoc 与运行时校验，不要求迁移 TypeScript。

| 对象 | 必须携带的信息 | 约束 |
| --- | --- | --- |
| SourceFact | id、原始条目、规范字段、section、entity、source、confirmed、conflict、origin、profileVersion、textVariants | 原文、来源和旧条目保留；无依据不生成 |
| Record | recordId、domain、anchorFacts、fieldFacts、顺序、可用性、缺项 | education/work/project/language/award 分开；同名不等于同一记录 |
| FieldDescriptor | snapshotId、fieldId、sectionId、recordId、语义及依据、controlFamily、valueState、required、约束、可见性 | DOM 下标不充当跨扫描稳定身份 |
| ControlRef | 根节点、触发器、编辑器、选中显示、关联菜单、选项、失效条件 | 读取、执行、回读使用同一组件契约 |
| FillPlan | taskId、tab/document 身份、snapshotRevision、profileRevision、binding、操作清单、前置值 | 计划过期或作用域改变必须重建 |
| ExecutionReceipt | taskId、fieldId、阶段、是否尝试、结果、原因、时间、版本 | written 与 verified 分开 |
| BaselineSnapshot | 私有完整原值、逻辑字段映射、恢复动作、覆盖检查 | 不进入普通日志与公开仓库 |

`valueState` 至少区分 empty、committed、search-only、unknown、disabled；读取失败不能自动等同空白。

规范化只能处理明确等价的格式，例如年月补零、换行编码。不得删减正文、变更数字或把仅显示名称视作后台提交值已正确。

### 6.2 资料可用性与迁移

- 在现有 fact/entity/profile-library 之上增加记录视图，保留旧 id、确认状态、来源与站点限定；不强迫用户重写 JSON 或重新上传已保存内容。
- 每个分区分别显示“原始条目数、规范字段数、可绑定记录数、缺少锚点/日期/正文数、冲突数”。
- 旧项目片段恢复沿用 0.13.0 原句预览。已保存部分整理后继续使用；从未保存过的内容仍需有来源补入。
- 页面学习须先预览：原状备份与“确认为以后可复用事实”是两件事。整页既有值不能无审核变成全局资料。
- 教育、公司、项目、语言、奖项分别建记录；年份或专业相同不能合并记录。
- 页面需要“项目角色”“项目描述”“项目中职责”时分别选对应资料。禁止将同一长段复制到所有字段。
- 多简历版本独立；切换版本导致旧 plan 失效，不能跨版本混填。岗位相关变体必须显示所用版本。
- 日期保留年/月/日精度与至今标记，缺月不补 1 月，缺日不补 1 日。
- 迁移按备份 → 预览差异 → 一次提交 → 回读校验执行；中断能回滚，不删除旧格式原文。

### 6.3 页面区域与字段识别

先确定申请表主体、分区与记录，再识别字段。排除导航、职位搜索、侧边目录、插件自己的 UI、隐藏副本、菜单搜索框以及提交/同意控件。

标签优先顺序：有效关联标签/ARIA → 组件外部真实字段标题 → 记录内局部结构 → 有含义 placeholder → 有边界的附近文本。通用“请输入/请选择”、已有值、校验报错与菜单内容不得成为字段名。

对于 Moka，`label.sd-Input-container` 可能只是组件壳，并非业务字段标题；不能因为它是 label 就截断查找。必须找到相邻的姓名、专业名称、就读时间等真实标题，同时避免跨卡片借标签。

section 与 record 身份结合正文边界、局部新增按钮、锚点字段与重复结构；同名侧边目录不参与绑定。多层相似结构无法唯一确定时留下具体原因，不选第一个节点。

视觉位置只作受限局部消歧证据，不能凭坐标猜个人事实。识别置信度用可解释等级和依据列表，不输出无标定的 0.96 等伪概率。

### 6.4 Moka 组件适配

新增 Moka 组件族，优先处理现有页面真实观察到的前缀，避免依赖构建后缀：

- 组件根：`[class*="sd-Dropdown-container"]`，并核对内部角色，避免把所有 dropdown 都当普通单选。
- 输入壳：`[class*="sd-Input-container"]`、`[class*="sd-Select-container"]`。
- 已选显示：`[class*="sd-Input-display-value"]`。
- 菜单/日期候选：参考包中出现 `sd-Select-menu`、`sd-Menu-content-item`、`sd-panal-menu-wrapper`、`sd-basic-selector-year` 等。它们尚未在本轮展开的真实菜单中确认，实施必须观察真实菜单后才启用。

每种适配器提供 discover/canonical/read/open/search/choose/verify/cancel；必要时区分普通单选、可搜索学校/专业、年月选择、日历、地区层级和多选。

执行顺序为：确认唯一目标 → 打开目标控件 → 关联本次菜单 → 如需搜索再输入 → 等待候选稳定 → 选择精确且唯一的合法候选 → 失焦 → 回读选中显示 → 等待框架更新后再核验。不能全页面取第一个同文案选项。

菜单为空、只有加载中、候选重复、选中后回弹、需要上级地区、虚拟列表尚未呈现、节点被替换分别返回不同原因。支持范围中的动态选项失败必须进入修复，不能永久改成“人工”绕过验收。

保留原生 setter 与输入事件路径，但不能直接写内部搜索框后判成功；普通 DOM API 无法通过的组件不擅自调用 React 私有对象。范围内需要额外页面桥接时先明确事件协议、来源校验和最小输入，独立验证，不能照搬第三方 MAIN-world 桥接整包。

### 6.5 重复记录与新增

教育、工作/实习、项目、语言、奖项是本次完整 Moka 范围。不能只做前三类后声称“整表完成”。

绑定顺序：已确认的整段绑定 → 唯一且一致的锚点 → 唯一剩余记录 → 一次展示待对应记录。不能仅凭 DOM 第 n 项与资料第 n 项就隐式绑定。用户显式选择按资料顺序分配空白记录时，预览并固定本次映射。

新增基于来源记录数与已识别卡片数的差，不以原始 fact 数为目标。每次新增后验证恰好增长一张卡、旧卡片值不变、新卡身份明确，再继续。无增长、增长多张、旧值被重置或结果未知时停止新增并回读。

同一 task 不并发操作两个弹出控件或同一分区卡片。第二次点击填写必须幂等，不重复新增、不重写已有一致值。

### 6.6 执行调度与性能

- 可并行进行纯资料匹配、日志摘要等无页面副作用计算；UI 变更按记录和依赖串行。
- 缓存以 document、分区结构和 profile revision 为边界；DOM 改动后局部失效，禁止复用失效节点。
- 每次写入前核对目标、已有值、资料版本和绑定；存在新编辑则暂停该字段。
- 等待基于可观察条件、取消信号与总 deadline，避免无界重试。自动重试最多一次，且只在回读证明没有产生动作时进行；未知结果不得重试新增。
- 延续现有 500 ms 最终回读保护，优化集中于无效遍历、重复匹配与固定等待，不用删回读换速度。
- 建议初始预算：动作开始 300 ms 内反馈；暖态扫描+计划在同机夹具 p95 ≤ 1.5 s；100 个逻辑目标整轮自动执行 ≤ 90 s（人工等待单独统计）；取消请求 500 ms 内被调度器接收且此后不启动新写入。均为拟定验收预算，不是已测成绩。
- 远端候选服务造成等待时分别记录网络候选等待与本地执行耗时，超时给具体控件原因。
- 与旧版和参考插件的速度对照必须同浏览器、同页面初态、同字段集合、同资料、同成功判定。没有实际运行参考插件时只做静态对照，不宣称更快。

## 8 产品交互

### 8.1 主要流程

页内唯一主操作为“填写简历”。显示当前使用的简历版本、已识别分区和可用记录数量；不要求用户先理解扫描、匹配、协议和绑定内部术语。

正常情况下点击一次后自动识别并补填有明确依据的空白字段；不能因少量未知项阻塞其他分区。有歧义时一次集中展示整段经历对应，而非逐字段弹窗。新增权限、资料恢复、版本冲突只在相关步骤出现。

状态必须区分：

- 正在识别 / 正在填写 / 正在核对；
- 已填写且页面回读通过；
- 原有内容保留，尚未验证；
- 资料缺少 / 控件未支持 / 需要选择经历；
- 已停止，已完成多少项；
- 没有可填项，并展示主要原因与可执行入口。

`ok: true`、`completed`、`no-eligible-fields` 不能直接映射同一个绿色成功提示。37 项 preserve 不能计成 37 项新填成功。

“更多操作”保留：读取本页已填内容并核对、记住手动补充、资料管理、日志、只读检查、备份恢复。高级 MCP/加密库收拢但不删除。开发测试用清空/恢复入口与日常填写分离，避免普通用户误触。

### 8.2 结果核对

按分区显示“计划数 / 尝试数 / 回读通过数 / 保留数 / 待处理数”；点击问题定位到对应记录与字段。提示举例：“第 2 段教育的专业已打开，但未找到唯一候选”，并给“重新选择资料/查看候选/查看日志”中适用的操作。

默认不对所有字段加第二次确认；明确冲突、覆盖已有内容、整段歧义或来源冲突才要求核对。对于岗位标题与当前简历版本方向不一致，提示检查版本，不自动改写事实或更换附件。

人工补齐后，用户可一次核对新增资料并存入当前版本。保留来源与 origin，不能自动监听所有输入后永久学习。

## 9 日志与故障闭环

### 9.1 统一关联

沿用 taskId 作为一次用户操作的主关联键，不再并行发明另一套无映射 runId。scan/add/bind/plan/fill/verify/stop/summary/export 都关联同一任务；复测产生新任务并引用前次缺陷编号。

每任务终态必须有一个摘要，包括分母、成功/保留/失败/未知、新增卡片数量、取消情况、日志 dropped/omitted 与阶段耗时。partial、no-eligible-fields、failed、cancelled 明确分开。后台重启、页面导航或失联留下 interrupted/unknown，不把没有结束日志自动当失败或成功。

字段标识只在测试会话/任务中稳定，不需要把原 DOM 路径、账号或持久用户标识发到普通日志。

### 9.2 分开保存三类证据

1. **普通插件日志**：白名单规范字段、阶段、计数、原因、版本与耗时；不含个人值、原始标签、完整网址、简历正文、Cookie、令牌、文件路径和异常原文。
2. **私有现场记录**：baseline、真实字段与 sessionFieldId 对应、必要截图，仅本机保存，用于本次获授权的恢复和排查。
3. **公开缺陷夹具**：将现场问题缩成虚构数据 HTML 与测试，保留结构及事件行为；不能直接发布真实页面全文或截图。

本地自动记录与旧诊断模式分别注明来源，修正过时的默认开关/保留容量说明。保留有界队列、24 小时读取清理和不阻塞填写的设计；导出时按当前 task 固定快照并分批生成，不能因长日志卡死主入口。真实测试每轮结束立即导出，避免 80 条滚动记录截掉任务前半段；后续容量变更需按字节预算验证。

只读网页 console 与插件结构化日志分别标 source。控制台警告不能替代插件失败回执。网页标签、console 文本及导入材料中的指令均按数据处理。

### 9.3 每个失败必须回答的五个问题

- 在哪个版本、哪个宿主、哪一个任务发生？
- 哪个分区/记录/规范字段，已有值状态和资料状态是什么？
- 失败在识别、来源、绑定、新增、打开、搜索、选择、写入、回读还是日志层？
- 最小可复现条件是什么？旧版同条件是否失败？
- 修复后相同条件是否通过？是否造成新增回归？

没有这些证据就保留“待定位”，不要凭一次 unknown 日志大幅重写所有模块。

## 10 实机执行步骤

以下全部属于实施阶段，本轮未执行。

1. **核对版本与宿主。** 记录第 3、4 节身份，确认实际页仍为用户目标，不改变登录态。
2. **先完整记录。** 生成第 5 节私有备份、字段地图、分区截图；核对记录数量、原有附件和开关。
3. **准备真实来源。** 从已有资料及已确认的页面事实建立本次期望表；缺项与不可恢复项单列。不能在清空后才发现资料库没有学校/日期。
4. **先复现旧行为。** 在虚构或私有隔离副本上保存旧版基准，证明已观察问题；真实页第一次只读检查，不为了基线多次破坏表单。
5. **确认恢复与站点副作用。** 所有清空硬条件通过，再进入字段清空轮。
6. **清空限定字段。** 经正常控件动作清空，独立回读形成实际清空列表；附件、照片与提交相关控件保持原状。
7. **点击插件填写。** 用户可见内置浏览器中的插件主入口；不由 Codex 逐字段代写。保留 UI 状态和 taskId。
8. **独立验收。** 核对表单最终显示、必填错误、跨记录一致性、日期精度、文本完整性与残留搜索词；需要时在已确认无保存副作用的正常 UI 预览检查，不能点击“预览并提交”来试探。

10. **迭代。** 最小复现 → 修改对应层 → 单元/组件/安装回归 → 只复测受影响真实步骤。修复记录明确引用旧失败，不删除失败用例。
11. **新增记录轮。** 完成教育/工作/项目/语言/获奖全部新增夹具与安装验证，再执行符合第 5 节条件的真实缺卡片场景。
12. **幂等、取消与恢复。** 第二次填写不重复新增，取消后不继续写；恢复原状并独立比对。
13. **交付同步。** 本地指定目录、GitHub 功能提交、完整安装包与验证报告一致；任何现场未完成项保持明确状态。

一个控件受阻时继续处理其他已授权可执行分区和代码工作。若所有剩余真实写入都依赖尚未具备的宿主能力或恢复条件，可停止该部分，但报告不能写“整项目已完成”。

### 11.2 统计分母

现场先冻结目标清单，逐字段标明“可编辑、有明确来源、原为空/本轮清空、可由插件操作”。新增卡片出现的字段按记录契约补入清单并记录分母变化原因。

- 自动成功率 = 独立回读确认正确的插件写入数 / 本轮冻结的应自动填写目标数。
- 原值保留率、资料覆盖率、字段识别率、必填覆盖率分别计算。
- 未识别但属于目标范围的字段计失败，不能从分母删掉。
- 缺来源、禁用派生值、附件、同意/提交项列单独清单，不伪造可填能力。
- 由人工或 Codex 补填的项不计插件成功。
- 本次 Moka 支持范围内、有确认来源的目标要求 100% 正确回读；错填、串记录、未知结果均为发布阻断。
- 0 次错误覆盖、0 次重复新增、0 次提交/撤回申请、0 次公开个人数据泄露。
- 范围外站点不能借该成绩宣称全站兼容。

### 11.3 测试执行

本轮不运行业务测试。实施时使用 0.13.0 基线实际存在的脚本，并按改动选择，不在旧主目录运行不存在的命令。

基础门槛：`npm test`、`npm run build:engine`、`npm run check`。控件改动运行 `test:components`；资料恢复运行 `test:readiness` 与 `test:readiness-mv3`；新增流程运行 `test:empty-records` 与 `test:empty-mv3`；消息/存储/主入口改动覆盖已有 local/page/MCP 安装流程。新增 Moka 用例按本节矩阵注册到现有测试和 CI。

每个真实缺陷先补一个旧版失败、新版通过的行为用例。验证输入最终值、显示值、记录归属和动作次数，不能只断言函数返回 true。生成版引擎与生产安装版都须包含该修复。
